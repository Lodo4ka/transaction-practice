# Load Testing Transaction Strategies

Этот документ описывает как запускать нагрузочное тестирование различных стратегий транзакций.

## Подготовка

### 1. Настройка тестовой базы данных

Создайте тестовую базу данных PostgreSQL:

```sql
CREATE DATABASE transaction_test;
```

### 2. Применение миграций

```bash
# Примените миграции к тестовой базе
DATABASE_URL="postgresql://postgres:password@localhost:5432/transaction_test" npx prisma migrate deploy
```

## Запуск тестов

### Интеграционные тесты с реальной базой данных

```bash
# Запуск всех интеграционных тестов
npm run test:load

# Запуск конкретного теста
npm run test:load -- --testNamePattern="pessimistic lock"
```

### Доступные тесты

1. **10 транзакций с пессимистичной блокировкой** - базовый тест
2. **50 транзакций с оптимистичной блокировкой** - средняя нагрузка
3. **100 транзакций с атомарной блокировкой** - высокая нагрузка
4. **200 транзакций с изоляцией** - очень высокая нагрузка
5. **Сравнение производительности** - все стратегии
6. **Ступенчатые запросы** - имитация реальной нагрузки
7. **Экстремальная нагрузка** - 500 транзакций

## Метрики производительности

Каждый тест выводит:

- **Время выполнения** - общее время в миллисекундах
- **Успешные транзакции** - количество успешно выполненных
- **Неуспешные транзакции** - количество неудачных
- **Процент успеха** - отношение успешных к общему количеству
- **Среднее время на транзакцию** - производительность
- **Балансы до и после** - проверка целостности данных

## Стратегии транзакций

### 1. PESSIMISTIC (Пессимистичная блокировка)
- Использует `FOR UPDATE` для блокировки строк
- Хорошо подходит для высокой конкуренции
- Может вызывать deadlock'и

### 2. OPTIMISTIC (Оптимистичная блокировка)OPTIMISTIC (Оптимистичная блокировка)
- Использует версионирование для контроля изменений
- Быстрее при низкой конкуренции
- Может требовать повторных попыток

### 3. ATOMIC (Атомарные операции)
- Использует raw SQL для атомарных изменений
- Максимальная производительность
- Меньше контроля над изоляцией

### 4. ISOLATION (Максимальная изоляция)
- Использует SERIALIZABLE уровень изоляции
- Максимальная безопасность
- Может быть медленнее

## Анализ результатов

### Ожидаемые результаты

1. **PESSIMISTIC**: Хорошая производительность, возможны deadlock'и
2. **OPTIMISTIC**: Быстрая при низкой конкуренции, медленнее при высокой
3. **ATOMIC**: Максимальная скорость, минимальные конфликты
4. **ISOLATION**: Надежность, но медленнее

### Критерии выбора стратегии

- **Высокая конкуренция**: PESSIMISTIC или ATOMIC
- **Низкая конкуренция**: OPTIMISTIC
- **Критическая безопасность**: ISOLATION
- **Максимальная производительность**: ATOMIC

## Мониторинг

### Логи базы данных

```sql
-- Просмотр активных транзакций
SELECT * FROM pg_stat_activity WHERE state = 'active';

-- Просмотр блокировок
SELECT * FROM pg_locks WHERE NOT granted;
```

### Метрики производительности

- Время выполнения транзакций
- Количество deadlock'ов
- Количество повторных попыток
- Использование CPU и памяти

## Troubleshooting

### Ошибки подключения к базе

```bash
# Проверьте подключение
psql -h localhost -U postgres -d transaction_test

# Проверьте переменные окружения
echo $DATABASE_URL
```

### Ошибки миграций

```bash
# Сбросьте базу данных
DATABASE_URL="postgresql://postgres:password@localhost:5432/transaction_test" npx prisma db push --force-reset

# Примените миграции заново
DATABASE_URL="postgresql://postgres:password@localhost:5432/transaction_test" npx prisma migrate deploy
```

### Таймауты тестов

Увеличьте timeout в тестах или уменьшите количество транзакций для отладки.
